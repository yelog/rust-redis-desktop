# AGENTS.md

## Project Shape
- Single Rust package, not a Cargo workspace. `src/main.rs` wires the Dioxus desktop app; `src/lib.rs` re-exports modules for tests.
- UI is Freya/Dioxus under `src/ui/`; Redis protocol and data operations are under `src/redis/`; saved connection/config handling is under `src/config/` and `src/connection/`.
- Platform-specific behavior is real: tray support is excluded on Linux, Windows uses a WebView data directory and `build.rs` embeds `icons/icon.ico`, macOS bundle packaging uses `Info.plist` templates.

## Commands
- Run the app locally with `cargo run`; release binary build is `cargo build --release`.
- Run all Rust tests with `cargo test`.
- Run a focused Rust test/module with normal Cargo filters, for example `cargo test tests::connection_tests` or `cargo test serialization::`.
- There is no repo task runner, rustfmt config, clippy config, or pre-commit config; use plain Cargo commands unless a change adds new tooling.

## Redis-Backed Test Scripts
- Shell integration tests live in `test/` and require Docker plus `redis-cli` on the host.
- Start fixtures from `test/`: `./start-all-services.sh basic` for standalone Redis/test data, or `./start-all-services.sh all` for cluster, sentinel, SSL, and Redis Stack coverage.
- Run the scripted workflow from `test/` with `./run-tests.sh`; useful flags are `--skip-data`, `--skip-unit`, and `--skip-integration`.
- Connection-mode checks are separate: `./test-connections.sh direct`, `sentinel`, `ssl`, `cluster`, or `all`. SSH tunnel coverage uses `./test-ssh-tunnel.sh`.
- The Docker compose file publishes standalone Redis on `6379`, master/slave on `6380`/`6381`, TLS on `6382`, Redis Stack on `6383`, cluster nodes on `7000`-`7005`, sentinel on `26379`, and SSH on `2222`.

## Runtime State
- The app writes `config.json` under `dirs::config_dir()/rust-redis-desktop`; on macOS this is `~/Library/Application Support/rust-redis-desktop/config.json`.
- Saved credentials are encrypted before disk writes. Tests that touch storage should prefer `ConfigStorage::new_temp()` instead of the real platform config path.
- Updater state is separate from `config.json`: `src/updater/config.rs` stores `update.toml` in the same platform config directory.

## Release And Packaging
- GitHub releases are tag-driven: `.github/workflows/release.yml` runs on `v*` tags and installs Rust nightly in CI.
- macOS packaging flow is `scripts/setup-sparkle.sh`, then `scripts/build-app.sh <version> <build_number> <target>`, then `scripts/create-dmg.sh <version> <arch>`; Sparkle appcast/update manifests are generated by scripts in `scripts/`.
- Linux local packaging is `scripts/build-linux.sh [version]`; it builds release, prepares an AppDir/AppImage when `appimagetool` exists, and creates a `.deb`.
- Windows release packaging builds `cargo build --release`, then uses NSIS with `scripts/installer.nsi` and bundles WebView2 setup plus any emitted `.dll`/`.dat` sidecars.
- The repo-local OpenCode release skill is under `.opencode/skills/release/`, but verify it against `.github/workflows/release.yml` before following artifact details; the workflow currently creates a Windows installer `.exe`, not a portable ZIP.

## Generated Or Local Artifacts
- Do not commit `target/`, downloaded `Frameworks/`, generated test cert/key directories under `test/`, `dmg-build/`, or local packaging outputs unless explicitly requested.
- `test/redis-ssl-certs/`, `test/ssh-keys/`, and `test/ssh-config/` may be generated by test setup scripts and are gitignored.
